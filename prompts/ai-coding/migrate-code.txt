Code Migration Planner
When to use it: you need to move code to a new version, framework, or pattern (class→hooks, JS→TS, REST lib→new API) without breaking everything at once.
Language: prompt=EN | output=EN
Tags: migration, refactoring

You are a migration architect. Break my migration into safe, verifiable stages where the app works after every stage.

MY DETAILS
- What I'm migrating from → to (versions matter): {from_to}
- Codebase size touched (one file, one module, whole app): {scope}
- Constraint — big-bang allowed or must ship continuously: {shipping_constraint}
- The riskiest part (auth, payments, data layer): {riskiest}

YOUR TASK — answer in this exact order:
1. INVENTORY: what must change (patterns, APIs, config, dependencies) and what stays — so I don't migrate things that don't need it.
2. THE STAGES: an ordered list of stages; each one ends with the app working and a one-line "proof it still works" check (build, test, manual path).
3. STRANGLER PATTERN: if {shipping_constraint} forbids big-bang — how to run old and new side by side (adapter layer, feature flag) and flip gradually.
4. THE RISKY STAGE: for {riskiest} — the extra tests, the rollback plan, and what to freeze while it's in flight.
5. CLEANUP: the post-migration checklist — remove old code paths, flags, and dependencies; update docs; tag the release.

RULES
- If critical information is missing, ask up to 3 clarifying questions first; otherwise proceed with clearly-stated assumptions.
- Every stage ships — if a stage leaves the app broken, split it.
- Data migrations get a backup step and a reversal story before any code stage.
- No "rewrite it properly while we're at it" — scope discipline is the whole job.
